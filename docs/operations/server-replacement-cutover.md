# 服务器版本替换与回滚清单

> 本清单用于“现有线上 PostgreSQL 版本 → 新版三服务系统”的正式替换。
> 2026-08-30 已对线上数据库做只读快照并在本机完成升级演练；尚未修改或部署服务器。

## 一、当前本地演练结论

- PostgreSQL 17 双测试库健康，42 条正式迁移可从空库完整执行。
- 迁移后的数据库结构与权威 PostgreSQL schema 对比结果为 `No difference detected`。
- SQLite 的 32 张业务表全部复制并逐表逐字段核对通过；`Session` 按设计不复制。
- 本次样本包含 66 个账号、201 个客户、33 个订单、515 条每日数据和 523 个数据版本。
- 账号用户名与密码摘要全部一致；9 类演示账号均能使用原密码登录 PostgreSQL 演练后端。
- 演练发现并修正了 PostgreSQL 枚举回填类型错误、报表模拟数据重复组长和结构核对命令漏传本地库地址三个问题。
- 2026-08-30 又对线上 PostgreSQL 做了只读在线快照，并在本机隔离库完成恢复：线上基线为 27 条迁移，候选版本新增的 15 条迁移全部成功，最终达到 42 条且结构无漂移。迁移前后的 52 个账号、6 个小组、31 个渠道、47 个批次、309 个客户、32 个订单、794 条旧事件及有效开单金额一致；账号密码字段和客户三岗归属摘要一致。39 条历史充值/出金记录完整复制到独立资金表。新版后端连接升级后的真实数据副本后，管理员、部门管理员、资源部、组长、接粉、炒群和专家的代表接口均返回 200。

大白话：本地演示数据和线上真实数据快照都已经完整模拟过“搬家”，箱子数量和箱内内容都对上了；但正式切换仍必须在停止写入后再做最终备份，在线快照不能代替停机切换点。

## 二、正式替换前的硬性条件

以下任一项未完成，都不得切换线上流量：

1. 明确维护窗口、执行人、复核人和回滚负责人。
2. 固定要发布的 Git 提交，确认后不再临时混入功能修改。
3. 取得服务器当前 PostgreSQL 数据库、环境配置、Nginx 配置和当前发布目录的完整备份，并把备份复制到服务器之外。
4. 对备份计算校验值，并实际在隔离目录恢复一次，不能只确认“备份文件存在”。
5. 确认现有数据中每个小组最多一名在职组长；发现冲突时先由业务确认现任人员，不自动删账号。
6. 在服务器同版本 PostgreSQL 的隔离库中重跑：恢复备份、执行迁移、全字段对账、结构漂移检查和旧账号登录测试。
7. 保留当前线上应用版本、原 SQLite 文件和原启动配置，整个观察期内不得清理。

## 三、正式切换顺序

1. 进入维护窗口，先停止所有会写数据的后台和前端入口。
2. 确认旧系统已经没有新的写入，再生成一份“最终 PostgreSQL 自定义格式备份”。
3. 记录最终备份的文件大小、校验值和生成时间。
4. 先把最终备份恢复到隔离数据库，再执行仓库内登记的正式 migrations，不手工跳过失败项。
5. 对隔离数据库执行结构漂移检查、旧账号登录和代表接口冒烟；全部通过后，才允许对正式库执行同一批 migrations。
6. 核对迁移前后的全部业务表行数和关键字段摘要，并单独核对：
   - 账号数量及用户名/密码摘要；
   - 公司、部门、小组、岗位和配对历史；
   - 客户、活动、订单和客户资金事件；
   - 每日数据、每个版本及统计金额；
   - 旧会话不作为业务数据迁移依据；切换后所有账号重新登录。
7. 启动新版后端、前台和管理端，但先不切换公网入口。
8. 使用原账号分别登录：总公司管理员、公司管理员、部门管理员、资源部、组长、接粉、炒群、专家。
9. 逐项冒烟检查：账号管理、组织范围、每日数据、客户进度、渠道汇总、客户资金和只读权限。
10. 所有检查通过后才切换同一域名的反向代理入口，并保留旧服务为停止状态，不立即删除。

## 四、继续使用现有域名的入口规则

正式上线不新增域名，现有域名按路径分流：

- `/api/` 转发到新版后端 `127.0.0.1:3003`；
- `/admin` 与 `/admin/` 转发到新版管理端 `127.0.0.1:3002`；
- 其余路径（包括 `/`、`/login`、`/change-password`）转发到新版一线端 `127.0.0.1:3000`。

管理端必须使用 `APP_BASE_PATH=/admin` 重新构建。后端保持 Cookie 的 `Path=/`，这样同一个账号从根登录页进入 `/admin` 后仍保持登录。Nginx 切换前必须先执行 `nginx -t`；路径分流只允许一次性 reload，不直接覆盖后跳过检查。

大白话：地址栏还是现在那个网址。普通员工登录后留在首页，管理员登录后进入同一网址后面的 `/admin`，三个程序在服务器内部各跑各的，用户看不出换了三个服务。

## 五、上线后的观察

- 首小时持续检查登录失败、500 错误、数据库连接、慢查询和磁盘空间。
- 抽查新写入的每日数据、客户进度和资金记录能刷新到对应汇总。
- 抽查至少一个跨时区小组的“今日、近 7 天、当月”日期边界。
- 观察期内禁止清理旧 SQLite、旧发布目录和最终备份。

## 六、回滚规则

### 尚未开放新系统写入

停止三个新版服务，恢复旧服务和旧 Nginx 入口；数据库尚未产生新版写入时，恢复迁移前状态并验证旧账号登录及关键页面。

### 已经开放并产生新数据

不能直接切回旧应用，否则新版写入的字段可能被旧版忽略。应先停止所有写入，保全 PostgreSQL 快照，列出切换后新增/修改记录，再决定回退数据库迁移或修复后继续使用新版。未经对账不得覆盖生产库。

大白话：刚切换、还没人填数据时可以直接退回旧房子；已经有人在新房子里放了东西，就必须先把新增东西清点出来，不能直接锁门走人。

## 七、明确禁止

- 不在用户仍可录入时制作最终切换备份或执行正式迁移。
- 不把本地演示数据库当作生产备份。
- 不为通过迁移而临时删除账号、客户、订单或资金记录。
- 不复制旧登录会话；切换后所有账号重新登录一次。
- 不在没有最新异机备份和已验证回滚版本时部署。
